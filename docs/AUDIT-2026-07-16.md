## 1. Architecture & Dependency Hygiene — A− (9/10)

**Strengths:**
- Clean module separation: `core/` → `rag/` → `knowledge/` → `features/`
- 16 pure-Dart modules identified (no Flutter/plugin imports) — fully unit-testable
- Dependency rule from `architecture.md` is mostly enforced
- `LocalLlm` abstract interface decouples chat from model implementation
- Singleton pattern for `modelManager`, `connectivityProvider`, `meshService`

**Issues found:**
- `lib/knowledge/kb_loader.dart` imports `package:flutter/services.dart` and
  `package:path_provider` — this breaks the "pure-Dart knowledge layer" rule
  from `architecture.md`. It's an adapter by necessity (rootBundle), but
  should be documented as an exception, not silently violating the rule.
- 89 Dart files in `lib/` is well-organized across 17 feature directories

**Verdict:** Architecture is sound. The one dependency violation is a known
adapter-layer compromise, not a design flaw.

## 2. Test Coverage & Quality — B+ (8/10)

**Strengths:**
- 307 tests passing (30 unit, 15 widget, 1 integration)
- New v2 features all have dedicated test files (eval, urgency, rumour, SOS, LoRA)
- Pure-Dart modules are thoroughly tested (decision tree: 9 tests, urgency: 13 tests)
- Widget tests cover key screens (triage wizard: 6, directory: 2)

**Gaps:**
- `lib/rag/` has 7 files but 0 dedicated test files in `test/unit/rag_*`
  (prompt_builder has tests, but keyword_retriever, retriever, types, urgency,
  rumour are tested via their own `*_test.dart` files — good, but the naming
  doesn't map 1:1 to the source files)
- `lib/core/` has 7 files but model_manager tests are sparse (LoRA test only
  tests setter/getter, not actual generation with LoRA)
- `lib/features/mesh_comm/` has 8 files but 0 test files matching by name
  (sos_payload, sos_relay, sos_relay_listener have tests — but mesh_service,
  mesh_models, mesh_radar_screen don't)
- `lib/features/safe_beacon/` has 3 files, only sms_queue has tests
  (safe_beacon_payload, safe_beacon_screen untested)
- Integration test requires a device — can't be run in CI

**Verdict:** Good coverage for a hackathon. The pure-Dart logic (where bugs
are most dangerous) is well-tested. UI and integration layers are thin.

## 3. Offline-First Integrity — A (9.5/10)

**Strengths:**
- Core chat loop has ZERO network calls — fully offline RAG + on-device Gemma
- Only 3 network paths exist: model download, optional Cloud AI fallback,
  optional weather tile — all gated and documented in AGENTS.md
- 23-chunk KB is bundled in the APK (`assets/kb/`) — no first-run network step
- `KeywordRetriever` is pure-Dart, sub-millisecond, surprisingly accurate
- 94% retrieval rate (47/50 test queries get at least one hit)
- `connectivityProvider` singleton is the single source of truth for online state

**Issues:**
- Vosk STT is a stub — voice input falls through to `speech_to_text` (online).
  This is the #1 offline gap. Documented but unfixed.
- Cloud AI fallback uses `gemma-4-31b-it` → correctly degrades to corpus when offline

**Verdict:** This is the project's strongest dimension. The thesis
"it works when the internet doesn't" is structurally enforced.

## 4. Bangla UI Compliance — A (9/10)

**Strengths:**
- All user-facing Text() strings are in Bangla
- Bengali numerals (০-৯) used consistently via `_bn()` helpers in triage,
  safe beacon, and directory screens
- Danda (।) used in prose
- English only in logs, code identifiers, and engineering docs (per AGENTS.md)

**Issues:**
- SOS SMS body uses Latin digits for casualty count (`3 জন` not `৩ জন`) —
  intentional trade-off for SMS operator readability, documented in test
- `emergency_contacts_screen.dart:446` has hint text `০১XXXXXXXXX` with Latin X's
  — acceptable for a phone format placeholder

**Verdict:** Near-perfect Bangla compliance. The two exceptions are
intentional SMS/format trade-offs.

## 5. Security & Privacy — A (9.5/10)

**Strengths:**
- No hardcoded secrets — Gemini API key via `String.fromEnvironment` only
- `api_key_store.dart` stores keys in platform-secure storage
- No analytics that ship user content off-device
- Voice, GPS, photos, chat queries never leave the device
- SMS body stays local until user explicitly sends
- No `eval()`, `exec()`, shell injection, or pickle deserialization vectors

**Issues:**
- None found

**Verdict:** Clean. Privacy-by-design is structurally enforced.

## 6. Error Handling & Robustness — B (7.5/10)

**Strengths:**
- Tier 2 (model) gracefully degrades to Tier 3 (corpus) on failure
- Tagged debugPrint logging (`[ChatRepo/Tier2]`) for runtime triage
- Model manager handles Range-resume, partial downloads, OOM prevention

**Issues:**
- Multiple bare `catch (_) {}` blocks that silently swallow errors:
  - `admin_broadcast_service.dart:119`
  - `device_capability.dart:108`
  - `model_manager.dart` (several)
  - `sound_service.dart:30`
- These should at minimum log, even in release — a swallowed error in a
  release APK is unrecoverable without a tag the user can grep for
- No `FlutterError.onError` / `PlatformDispatcher.instance.onError` handler
  for global error capture
- `debugPrint` is a no-op in release — errors vanish silently

**Verdict:** Functional but fragile. The silent-swallow pattern will make
on-device debugging harder than it should be.

## 7. Gemma Integration Depth — A− (9/10)

**Strengths:**
- Uses flutter_gemma 1.3.0 + flutter_gemma_litertlm 1.1.0 (latest modular SDK)
- `.litertlm` format with per-query session pattern (correct for 2B models)
- Context window 1024 (above the minimum), reply cap 512 via maxOutputTokens
- v2 additions use SDK features most teams won't:
  - `enableThinking` — adaptive reflex vs. deliberation
  - `loraPath` — hot-swappable fine-tune adapter
  - `tools` — function calling for structured SOS
- LoRA support is wired but adapter needs actual training (Colab pipeline ready)
- Rumour checker is a genuinely novel offline feature

**Issues:**
- SOS composer's AI-extract button is a placeholder (`TODO` at line 180) —
  actual function-calling session not wired yet
- Thinking mode is set but not measured — no before/after latency data yet
- LoRA adapter doesn't exist yet (training scaffold has 6 examples, needs 150+)

**Verdict:** The architecture is ready for all Gemma 4 capabilities.
The actual fine-tune + measurement is the remaining work.

## Rating Methodology

Each dimension scored on a 10-point scale:
- **9-10 (A/A+):** Production-grade, no significant issues
- **8-8.9 (B+):** Hackathon-excellent, minor gaps
- **7-7.9 (B):** Functional but has notable issues to address
- **6-6.9 (C):** Needs work before demo
- **Below 6:** Blocking risk

**Overall is a weighted average, not a simple mean.** Offline-first integrity,
Gemma depth, and test coverage are weighted higher because they directly
determine rubric scores.
